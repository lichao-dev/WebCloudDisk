# WebCloudDisk 第三方库编译与迁移指南

## 1. 文档目的

本文档记录项目当前使用的第三方库、系统依赖和可重复的编译命令。

第三方库源码保存在 `third_party/<library>/`；主项目自动编译的产物位于 `build/third_party/`，Workflow 和 wfrest 仍使用各自源码目录中的 `_include`、`_lib`，不再复制到统一的 `third_party/install` 目录。

项目移动到其他目录或其他 Linux 机器后，应在新环境重新编译需要编译的库，不要直接复用旧机器的 CMake 缓存和二进制文件。

Workflow 和 wfrest 需要提前在各自源码目录中编译；spdlog、OSS SDK、rabbitmq-c 和 SimpleAmqpClient 由主项目 CMake 随项目编译。

## 2. 当前依赖

| --- | --- | --- | --- | --- |

| jwt-cpp | 0.7.2 | 只有头文件 | 否 | JWT 生成和校验 |
| inih | 项目内单头文件版本 | 只有头文件 | 否 | INI 配置解析 |
| spdlog | 1.17.0 | 静态库 | 主项目自动编译 | 日志 |
| Workflow | 1.0.1 | 静态库和动态库 | 是 | 异步网络、MySQL 任务和任务调度 |
| wfrest | 0.9.9 | 静态库 | 是 | HTTP 服务器和路由 |
| sRPC | 0.10.4 | 静态库和代码生成器 | 是 | 微服务 RPC 通信和接口代码生成 |
| 阿里云 OSS C++ SDK V2 | 0.1.1 | 静态库 | 主项目自动编译 | OSS 容灾备份 |
| rabbitmq-c | 0.18.0 | 静态库 | 主项目自动编译 | AMQP 协议客户端 |
| SimpleAmqpClient | 2.6.0 | 静态库 | 主项目自动编译 | RabbitMQ C++ 包装层 |

sRPC 复用项目已有的 Workflow，并依赖 Protobuf、lz4 和 snappy；macOS 下通过 Homebrew 提供这三个系统依赖，
但 sRPC 源码、静态库和代码生成器都保留在 `third_party/srpc`，不安装到系统目录。
rabbitmq-c 必须先于 SimpleAmqpClient 编译，该顺序由主项目 CMake target 依赖自动保证。

## 3. 目录结构

完成编译后的主要目录如下：

```text
third_party/
├── inih/
│   └── INIReader.h
├── nlohmann_json/
│   └── include/nlohmann/
├── jwt-cpp/
│   └── include/jwt-cpp/
├── spdlog/
│   └── include/spdlog/
├── workflow/
│   ├── build/
│   ├── _include/workflow/
│   └── _lib/
│       ├── libworkflow.a
│       └── libworkflow.so
├── wfrest/
│   ├── build/
│   ├── _include/wfrest/
│   └── _lib/
│       ├── libwfrest.a
│       └── libwfrest.so
├── srpc/
│   ├── _bin/srpc_generator
│   ├── _include/srpc/
│   └── _lib/libsrpc.a
├── alibabacloud-oss-cpp-sdk-v2/
├── rabbitmq-c/
└── SimpleAmqpClient/
```

说明：

- `nlohmann_json/include` 和 `jwt-cpp/include` 是源码自带的头文件目录。
- `inih/INIReader.h` 是项目使用的单头文件版本，不需要单独编译。
- `workflow/build` 和 `wfrest/build` 保存需要提前编译的库及其中间文件。
- Workflow 和 wfrest 的上游 CMake 脚本会分别把头文件和库生成到各自的 `_include` 和 `_lib` 目录。
- sRPC 的中间文件位于主项目 `build/third_party/srpc-0.10.4-standalone/`，需要使用的头文件、静态库和生成器
  分别位于源码目录的 `_include`、`_lib` 和 `_bin`，这些构建产物均被 sRPC 自带的 `.gitignore` 忽略。
- spdlog、OSS SDK、rabbitmq-c 和 SimpleAmqpClient 的产物统一生成在主项目 `build/third_party/`，不写回源码目录。

## 4. 支持的环境

本文档中的命令已在下列环境验证：

- Ubuntu 24.04 x86-64
- GCC/G++ 13.3
- CMake 3.28
- OpenSSL 3.0
- macOS Apple Silicon、Homebrew、AppleClang 21、CMake 4.4

其他较新的 Ubuntu 或 Debian 版本通常也可使用。如果从 x86-64 迁移到 ARM64，或新机器的 glibc、OpenSSL、C++ 运行库版本不同，必须在新机器重新编译。

## 5. 安装系统依赖

Ubuntu/Debian 执行：

```bash
sudo apt update
sudo apt install -y \
    build-essential cmake \
    libssl-dev zlib1g-dev libboost-all-dev \
    protobuf-compiler libprotobuf-dev liblz4-dev libsnappy-dev
```

说明：

- `build-essential`：提供 GCC、G++ 和 Make。
- `libssl-dev`：Workflow、wfrest 和 jwt-cpp 需要 OpenSSL。
- `zlib1g-dev`：wfrest 需要 zlib。
- `libboost-all-dev`：SimpleAmqpClient 需要 Boost chrono；Boost 1.89 之前还需要 Boost system。
- `protobuf-compiler` 和 `libprotobuf-dev`：分别提供 `protoc`、Protobuf 头文件和链接库。
- `liblz4-dev` 和 `libsnappy-dev`：sRPC 的压缩模块以及主项目链接需要。
- 第一期不启用 Workflow Kafka 功能，不需要 zstd；LZ4 和 Snappy 仅为 sRPC 提供。

确认工具可用：

```bash
cmake --version
c++ --version
openssl version
```

macOS 使用 Homebrew 安装 sRPC 的系统依赖：

```bash
brew install cmake openssl@3 protobuf lz4 snappy
```

macOS 不需要也不应执行 Linux 的 `apt`、`ldconfig`，sRPC 也不执行 `sudo make install`。

## 6. 编译第三方库

所有命令都应在项目根目录执行：

```bash
cd /path/to/WebCloudDisk
PROJECT_ROOT="$(pwd)"
```

### 6.1 nlohmann/json

nlohmann/json 是只有头文件的库，无需编译。项目直接使用：

```text
third_party/nlohmann_json/include/nlohmann/json.hpp
```

### 6.2 inih

项目使用 `third_party/inih/INIReader.h` 中的单头文件版本，无需编译。业务代码只通过
`src/config/Config.cc` 读取 INI，其他模块使用解析完成的配置对象。

### 6.3 jwt-cpp

jwt-cpp 也是只有头文件的库，无需编译。项目直接使用：

```text
third_party/jwt-cpp/include/jwt-cpp/jwt.h
```

jwt-cpp 的加密和签名实现依赖 OpenSSL，最终业务程序仍需要链接 `OpenSSL::SSL` 和 `OpenSSL::Crypto`。

### 6.4 spdlog

spdlog 不需要提前单独编译。主项目通过 `add_subdirectory()` 使用源码，并关闭示例、测试、基准和安装规则：

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug -DBUILD_TESTING=ON
cmake --build build --parallel
```

主要产物：

```text
build/third_party/spdlog/libspdlogd.a  # Debug
build/third_party/spdlog/libspdlog.a   # Release
```

### 6.5 Workflow

Workflow 会同时编译静态库和动态库：

```bash
cmake -S third_party/workflow \
      -B third_party/workflow/build \
      -DCMAKE_BUILD_TYPE=Release

cmake --build third_party/workflow/build --parallel
```

主要产物：

```text
third_party/workflow/_include/workflow/
third_party/workflow/_lib/libworkflow.a
third_party/workflow/_lib/libworkflow.so
third_party/workflow/workflow-config.cmake
```

Workflow 构建时可能出现 `maybe be used uninitialized` 或 `ignoring return value of write` 警告。当构建最后出现 `Built target workflow-static` 和 `Built target workflow-shared` 时，这些警告不代表编译失败。

### 6.6 wfrest

wfrest 必须在 Workflow 编译完成后编译。显式传入 Workflow 的 package 目录，避免 CMake 去系统目录中查找：

```bash
cmake -S third_party/wfrest \
      -B third_party/wfrest/build \
      -DCMAKE_BUILD_TYPE=Release \
      -DWorkflow_DIR="${PROJECT_ROOT}/third_party/workflow"

cmake --build third_party/wfrest/build --parallel
```

主要产物：

```text
third_party/wfrest/_include/wfrest/
third_party/wfrest/_lib/libwfrest.a
third_party/wfrest/_lib/libwfrest.so
third_party/wfrest/wfrest-config.cmake
```

Linux 下的 `libwfrest.so` 是 GNU ld 链接脚本，不是 ELF 动态库。它会组合 `libwfrest.a`、zlib 和 `libworkflow.so`，这是 wfrest 0.9.9 的正常构建结果。

### 6.7 sRPC

sRPC 0.10.4 源码保存在 `third_party/srpc`。它不递归引入自己的 Workflow、lz4 和 snappy 副本：Workflow 复用
项目现有构建产物，LZ4、Snappy 和 Protobuf 使用当前平台的系统安装。所有命令都从项目根目录执行。

Ubuntu/Debian 先确认 Workflow 已在当前机器编译，再使用 `apt` 安装的 Protobuf、LZ4 和 Snappy 编译 sRPC：

```bash
test -f third_party/workflow/_include/workflow/Workflow.h
test -f third_party/workflow/_lib/libworkflow.a

WEB_DISK_PROJECT_ROOT="$(pwd)"
WEB_DISK_PROTOC_EXECUTABLE="$(command -v protoc)"

cmake -S third_party/srpc \
      -B build/third_party/srpc-0.10.4-standalone \
      -DCMAKE_BUILD_TYPE=Release \
      -DCMAKE_REQUIRED_INCLUDES="${WEB_DISK_PROJECT_ROOT}/third_party/workflow/_include" \
      -DWORKFLOW_INCLUDE_DIR="${WEB_DISK_PROJECT_ROOT}/third_party/workflow/_include" \
      -DWORKFLOW_LIB_DIR="${WEB_DISK_PROJECT_ROOT}/third_party/workflow/_lib" \
      -DWORKFLOW_VERSION=1.0.1 \
      -DProtobuf_PROTOC_EXECUTABLE="${WEB_DISK_PROTOC_EXECUTABLE}"

cmake --build build/third_party/srpc-0.10.4-standalone \
      --target srpc-static srpc_generator \
      --parallel
```

Ubuntu 发行版的 Protobuf 开发包可能不提供 `ProtobufConfig.cmake`；sRPC 在 Linux 上使用
CMake 内置的 `FindProtobuf` 模块，可以直接找到 `/usr/include` 和对应架构的系统库目录。

macOS 使用 Homebrew 依赖：

```bash
WEB_DISK_PROJECT_ROOT="$(pwd)"
WEB_DISK_BREW_PREFIX="$(brew --prefix)"

cmake -S third_party/srpc \
      -B build/third_party/srpc-0.10.4-standalone \
      -DCMAKE_BUILD_TYPE=Release \
      -DCMAKE_REQUIRED_INCLUDES="${WEB_DISK_PROJECT_ROOT}/third_party/workflow/_include;${WEB_DISK_BREW_PREFIX}/include" \
      -DWORKFLOW_INCLUDE_DIR="${WEB_DISK_PROJECT_ROOT}/third_party/workflow/_include" \
      -DWORKFLOW_LIB_DIR="${WEB_DISK_PROJECT_ROOT}/third_party/workflow/_lib" \
      -DWORKFLOW_VERSION=1.0.1 \
      -DOPENSSL_ROOT_DIR="${WEB_DISK_BREW_PREFIX}/opt/openssl@3" \
      -DCMAKE_PREFIX_PATH="${WEB_DISK_BREW_PREFIX}" \
      -DProtobuf_PROTOC_EXECUTABLE="${WEB_DISK_BREW_PREFIX}/bin/protoc"

cmake --build build/third_party/srpc-0.10.4-standalone \
      --target srpc-static srpc_generator \
      --parallel
```

两个平台都只构建项目需要的静态库和代码生成器。macOS 上 sRPC 0.10.4 的动态库 CMake 链接规则没有传播
Homebrew Protobuf 35 所需的 Abseil 依赖，因此本项目不构建也不使用 `libsrpc.dylib`。业务 target 后续必须通过
`protobuf::libprotobuf` CMake target 链接 Protobuf，不能只写裸的 `-lprotobuf`。

sRPC 0.10.4 上游强制使用 C++14，而 Homebrew Protobuf 35 要求 C++17。项目在
`third_party/srpc/src/CMakeLists.txt` 中保留一行集成补丁，将该编译选项改为 `-std=c++17`；不修改 sRPC
功能源码。

主要产物：

```text
third_party/srpc/_include/srpc/
third_party/srpc/_lib/libsrpc.a
third_party/srpc/_bin/srpc_generator
```

### 6.8 主项目自动编译的依赖

spdlog、OSS SDK、rabbitmq-c 和 SimpleAmqpClient 不需要提前执行独立的 `cmake --build` 或 `make install`。配置和构建主项目时，CMake 会在 `build/third_party/` 中按依赖顺序生成静态库：

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug -DBUILD_TESTING=ON
cmake --build build --parallel
```

SimpleAmqpClient 使用同一构建树中的 `rabbitmq::rabbitmq-static`，不会去系统目录查找或安装 rabbitmq-c。普通客户端测试只创建 AMQP 消息，不连接 RabbitMQ Broker。

项目保持 SimpleAmqpClient 的 `.cpp` 和 `.h` 功能源码不变，只在两个库的 `CMakeLists.txt` 中保留嵌入主项目所需的兼容补丁：子项目不覆盖主项目构建类型或全局编译选项，SimpleAmqpClient 优先复用同一构建树中的 rabbitmq-c target，安装规则只在独立构建 SimpleAmqpClient 时启用。Boost 查找优先使用其 CMake package config，找不到时回退到 CMake 的 `FindBoost` 模块，以兼容不同系统的 Boost 安装方式。

rabbitmq-c 0.18.0 会对 SimpleAmqpClient 2.6.0 使用的旧式兼容头文件输出弃用警告；这些头文件会继续转发到新版头文件，不影响编译结果。为避免维护额外的第三方功能源码补丁，项目保留该警告。

## 8. 在项目 CMake 中使用

Workflow 和 wfrest 继续直接引用预编译头文件与静态库；spdlog 使用主项目构建树中的 CMake target。

```cmake
find_package(OpenSSL REQUIRED)
find_package(ZLIB REQUIRED)
find_package(Threads REQUIRED)

set(THIRD_PARTY_DIR "${CMAKE_SOURCE_DIR}/third_party")

target_include_directories(server PRIVATE
    "${THIRD_PARTY_DIR}/inih"
    "${THIRD_PARTY_DIR}/nlohmann_json/include"
    "${THIRD_PARTY_DIR}/jwt-cpp/include"
    "${THIRD_PARTY_DIR}/workflow/_include"
    "${THIRD_PARTY_DIR}/wfrest/_include"
)

target_link_libraries(server PRIVATE
    "${THIRD_PARTY_DIR}/wfrest/_lib/libwfrest.a"
    "${THIRD_PARTY_DIR}/workflow/_lib/libworkflow.a"
    spdlog::spdlog
    OpenSSL::SSL
    OpenSSL::Crypto
    ZLIB::ZLIB
    Threads::Threads
)
```

`server` 要替换成项目实际的 CMake target 名称。

上面显式链接 `libworkflow.a` 静态库，因此运行时不需要通过 `LD_LIBRARY_PATH` 查找 `libworkflow.so`。OpenSSL、glibc 等系统库仍需要存在。

## 9. 如果选择 Workflow 动态库

如果将项目 CMake 中的：

```text
third_party/workflow/_lib/libworkflow.a
```

改为：

```text
third_party/workflow/_lib/libworkflow.so
```

运行时必须能找到 Workflow 动态库。开发环境可以临时设置：

```bash
PROJECT_ROOT="$(pwd)"
export LD_LIBRARY_PATH="${PROJECT_ROOT}/third_party/workflow/_lib${LD_LIBRARY_PATH:+:${LD_LIBRARY_PATH}}"
```

也可以在项目 CMake 中设置构建期 RPATH：

```cmake
set_target_properties(server PROPERTIES
    BUILD_RPATH "${THIRD_PARTY_DIR}/workflow/_lib"
)
```

检查最终程序的动态依赖：

```bash
ldd /path/to/server | grep -E 'workflow|ssl|crypto|z|not found'
```

## 10. 迁移到新机器

推荐流程：

1. 复制完整项目源码，确保 `third_party/nlohmann_json`、`jwt-cpp`、`spdlog`、`workflow`、`wfrest`、OSS SDK、rabbitmq-c 和 SimpleAmqpClient 源码完整。
2. `nlohmann_json/include` 和 `jwt-cpp/include` 是库源码的一部分，必须保留。
3. 不要把旧机器的主项目 `build`、`workflow/build`、`workflow/_lib`、`workflow/_include`、`wfrest/build`、`wfrest/_lib` 和 `wfrest/_include` 当作新机器的最终产物。
4. 安装第 5 节的系统依赖。
5. 按 Workflow、wfrest 的顺序完成提前编译，再使用新的空主项目 `build` 目录自动编译 spdlog、OSS 与 RabbitMQ 客户端库。
6. 使用第 7 节命令检查产物。
7. 重新配置和编译业务工程。
8. 如果使用动态库，运行 `ldd` 确认没有 `not found`。

Workflow 和 wfrest 生成的 `workflow-config.cmake`、`wfrest-config.cmake` 以及 CMake 缓存会记录绝对路径。即使 CPU 和操作系统相同，项目路径改变后也应重新执行 CMake 配置。

## 11. 常见错误

### 11.1 wfrest 找不到 Workflow

错误：

```text
Could not find a package configuration file provided by "Workflow"
```

处理方法：

1. 先配置和编译 Workflow。
2. 确认 package 文件已生成：

   ```bash
   test -f third_party/workflow/workflow-config.cmake
   ```

3. 配置 wfrest 时显式传入：

   ```bash
   -DWorkflow_DIR="${PROJECT_ROOT}/third_party/workflow"
   ```

### 11.2 找不到 OpenSSL

```text
Could NOT find OpenSSL
```

安装：

```bash
sudo apt install -y libssl-dev
```

### 11.3 找不到 zlib

```text
Could NOT find ZLIB
```

安装：

```bash
sudo apt install -y zlib1g-dev
```

### 11.4 移动项目后 CMake 仍引用旧路径

不要继续使用旧的 `build` 目录。在新的空构建目录中重新执行第 6 节的 CMake 命令。Workflow 必须先于 wfrest 重新配置。

### 11.5 链接时出现 undefined reference

确认下列事项：

- `libwfrest.a` 位于 `libworkflow.a` 之前。
- 已链接 OpenSSL、zlib 和 Threads。
- 头文件和库来自同一次构建。
- 没有同时混用 `/usr/local` 中的另一个 Workflow 或 wfrest 版本。

### 11.6 运行时找不到 Workflow

```text
error while loading shared libraries: libworkflow.so.1: cannot open shared object file
```

说明当前程序链接了 Workflow 动态库。可改为链接 `libworkflow.a`，或按第 9 节设置 `LD_LIBRARY_PATH`/RPATH。

## 12. 已验证范围

下列流程已实际验证：

- spdlog 1.17.0 能随主项目编译为 C++17 静态库。
- Workflow 静态库和动态库编译成功。
- wfrest 通过 `Workflow_DIR` 引用同级 `third_party/workflow` 并编译成功。
- OSS SDK、rabbitmq-c 0.18.0 和 SimpleAmqpClient 2.6.0 能随主项目编译为静态库。
- `cloud_disk_rabbitmq_client_tests` 能链接两个 RabbitMQ 客户端库并在不连接 Broker 时通过。
- `cloud_disk_rabbitmq_smoke_test` 能连接真实 Broker，以临时队列验证正式发布器、持久化消息、消费和手动 ACK，不访问 OSS。
- 经明确授权后，`cloud_disk_rabbitmq_oss_smoke_producer` 可配合 `cloud_disk_backup_worker` 验证业务队列和真实 OSS 上传。
- json、jwt-cpp、spdlog、Workflow、wfrest、OSS 与 RabbitMQ 客户端能在同一个 CMake 程序中编译链接。
- wfrest 官方最小 HTTP 示例启动后，`GET /hello` 返回 `world`。
